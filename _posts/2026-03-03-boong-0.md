# What is Blueprint?
Do you know all know what a **"Blueprint"** is?

I'm **not** talking about the kind of **blueprint** you see in architecture — like the classic building plan or technical drawing

| <img width="75%" src="https://images.ctfassets.net/s4ybdu2ld1ox/7KoNH8PR71vjj6zKJ2klLO/0ef16a934b9095f429392dfe0e9f16e3/home-blueprints.jpeg?w=1000&h=683&fl=progressive&q=70&fm=jpg&bg=transparent"> | 
|:--:| 
| *Not this* |

Blueprint is a **build framework** developed at **Google**

It borrows ideas from **Go(aka. golang)**, and unlike CMake or Makefiles, it's organized ardound **"modules"**(think of them like reusable library/package units), rather than one giant pile of build scripts
\
And If you feel like it, you can introduce new rules of your own and shape the whole thing into something **vendor-specific**, tailored exactly to your needs

On top of that, its syntax is pretty Bazel or GN-like, which makes it feel more approachable: simpler, cleaner, and more intuitive to reason about

One more fun detail: it doesn't build things *directly* like classic build tools
\
Instead, it **generates Ninja files first**, and then Ninja does the actual compilation
\
So in a way, it also gives off a slightly **GN-ish** vibe

And probably the most famous real-world ue of Blueprint is... **Android** — more specifically, **AOSP**

If you've ever poked around the Android source tree, you've definitely seen files like `Android.bp`
\
That's the configuration format used by **Soong**, and Soong is basically the poster child for the **Blueprint build framework** in action

| <img width="75%" src="../../../assets/images/2026-02-27/image.png"> | 
|:--:| 
| *Example from Android Runtime(aka. art)* |

To sum it up: Blueprint isn't a traditional **"static"** build system
\
It's delivered more like a **framework**, which makes it much easier to customize
\
And that flexibility is the big win — you can build (and evolve) your own build tooling in a way that's cleaner, and way more adaptable to your needs

# Quick Taste

As a quick taste, let's walk through a simple example of the `Build.bp` with `cc_binary` rule — and, under the hood, what kind of journey it takes through Go during the process

## Example of Build.bp

First off, the simplest "Hello World" in Blueprint syntax is probably using the `cc_binary` rule — it doesn't get much more staightforward than that

And if we toss in `cflags` for good measure, you can set up your `Build.bp` like this:
```
cc_binary {
    name: "hello",
    srcs: ["hello.c"],
    cflags: ["-O2"],
}
```

And since the `hello.c` we're building is just going to print a classic **"Hello, World!"**, it looks like this:
```c
#include <stdio.h>

int main(void)
{
    printf("Hello World\n");
    return 0;
}
```

Now we just need to take that `Build.bp` file and run it through the Blueprint framework, so it gets translated into a `build.ninja` file — something like this:
```
# ******************************************************************************
# ***            This file is generated and should not be edited             ***
# ******************************************************************************
#
#
ninja_required_version = 1.7.0

# # # # # # # # # # # # # # # # # # # # # # # # # # # # # # # # # # # # # # # #
# Module:  hello
# Variant:
# Type:    cc_binary
# Factory: github.com/PoppingBoba/boong/build.GetCBinary
# Defined: Build.bp:1:1

rule m.hello_.cc
    command = mkdir -p $$(dirname ${out}) && ${cc} -MMD -MF ${depfile} -c ${cflags} -o ${out} ${in}
    description = CC ${out}

rule m.hello_.link
    command = mkdir -p $$(dirname ${out}) && ${cc} ${ldflags} -o ${out} ${in}
    description = LINK ${out}

build obj/hello/hello.c.o: m.hello_.cc ../hello.c
    depfile = obj/hello/hello.c.o.d
    deps = gcc
    tags = module_name=hello;module_type=cc_binary;rule_name=cc
    cc = gcc
    cflags = -O2
    depfile = obj/hello/hello.c.o.d

build bin/hello: m.hello_.link obj/hello/hello.c.o
    tags = module_name=hello;module_type=cc_binary;rule_name=link
    cc = g++
    ldflags = 
default bin/hello
```
